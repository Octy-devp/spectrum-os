## 第二條 提交紀律（順序不可逆）

**任何 spectrum-os 變更的正規流轉，必須依序完成四步，不得跳步、不得換序：**

```
真本體 commit  →  push origin  →  ECC 側 git submodule update --remote  →  ECC 側 commit pointer
   (1)              (2)                        (3)                               (4)
```

| 步 | 動作 | 為什麼必須在這一格 |
|:---:|:---|:---|
| 1 | 在 `/home/octy/projects/spectrum-os` 提交（見第四條驗證後） | 唯一的寫入點 |
| 2 | `git push origin master` | 讓 commit 進入共享歷史——**這是「脫離孤兒」的唯一動作** |
| 3 | 在 ECC：`git submodule update --remote spectrum-os` | 讓唯讀 checkout 追上真本體 |
| 4 | 在 ECC 提交 pointer bump（訊息格式見第三條） | 消費者錨定版本 |

### 🔴 未 push 的本地 commit ＝ 孤兒風險

**本地 commit 不是保存，只是「還沒死透」。** 只要它還沒 push：

- 它只存在於這台機器的工作目錄；
- 它可能只靠 **detached HEAD** 支撐（submodule 尤其如此）——沒有 branch 指向它，`git checkout`、`git gc`、`git submodule update` 都可能讓它消失；
- 另一方（另一 checkout／另一 agent／人類）**完全看不見**它，因此會基於「不存在的歷史」做出決定；
- 交叉比對時，兩邊會各自聲稱自己的版本是「最新」。

**規則**：做完第 1 步後，**立即做第 2 步**，不要「攢一批再推」。需要多 commit 時，逐個 push 的成本遠低於事後考古。

### 🪦 事故墓碑：09-05 分叉的「兩邊獨有 commit 都未推」

見第一條。**雙分叉之所以能發生，前提正是「兩邊都沒 push」**——若有任一邊先 push，另一邊立刻會看到分歧。未 push 是分叉的**培養基**。

### 2.5 🔴 授權交接機制（本節的職能）

**先分清楚兩件事：本節不是「步 2 的例外」，是「步 2 的執行方式」。** 步 2（`push origin master`）的**必要性**不因本節而鬆動——未 push 仍是孤兒風險。本節改的只有一件事：**誰的手按下這個鍵，以及按下之前必須交接什麼。**

| | 內容 |
|:---|:---|
| **預設** | **agent commit 後停在本地**，將 commit hash 與待推內容交人類；push 由人類執行 |
| **授權代推** | 取得人類**明確授權**後，agent 可代推。**授權範圍僅限當次**——不得推定延續下一次 |
| **未經授權的 push** | **＝違律** |
| **未經授權的停住** | **＝違律**——停住只在「已交接」的前提下才是合法的（見 2.5.2）；原地不動、不出聲、不交接，不是「保守」，是**製造孤兒** |

#### 2.5.1 為什麼需要這一節：一個律與律的對撞

律文 v1.0 的第二條要求 `commit → push → submodule update → pointer`。但 **ECC 側 `AGENTS.md` §四 NEVER 表明文：「`git commit` / `git push` / … 必須由人類執行」**。

一個在光譜 OS 上工作的 agent，兩邊都讀，就會被兩條律夾住：

- **遵 spectrum-os 第二條** → 去 push → **違 ECC `AGENTS.md`**。
- **遵 ECC `AGENTS.md`** → 停在 commit → **違第二條** → 產生 **未 push 的本地 commit**——而第二條已經明文指出，未 push 的本地 commit 正是 09-05 分叉的**培養基**。

**這不是兩份文件誰對誰錯的問題，是律文 v1.0 的機制真空**：它規定了「必須 push」，卻沒規定「誰 push、怎麼交接」。**真空不會讓人守規矩，只會讓人各自發明做法**——而 09-05 已經證明，各自發明的做法就是雙分叉。

> **與 2.2 的關係（必須讀清楚）**：**2.2 的結論是「永遠 push」，2.5 的結論是「push 前要先交接」——兩者不是一半一半的折衷。** 一個「既不授權、也不交接、就地停住」的做法，**同時違反 2.2 與 2.5**，不是「折衷」。本節的存在是為了讓停住變成**可交接、可續、可調度的**狀態，而不是讓停住變成合法狀態。

#### 2.5.2 交接清單（缺一項即交接無效）

**停住不是一個靜默的狀態（那個叫孤兒），是一個有內容的交付。** 移交者必須同時交出以下四項：

| # | 項目 | 為什麼不能省 |
|:---:|:---|:---|
| 1 | **commit hash（完整 40 碼＋短碼）** | 沒有 hash 的「我改好了」＝要求對方自己去 git log 海裡撈 |
| 2 | **是否已推 origin** | 這一欄決定接手的人是「續推」還是「考古」——**09-05 的兩邊各自聲稱最新，就是因為這一欄沒人寫** |
| 3 | **第四條完整性驗證結果** | 乾淨 worktree 上的實跑結果（版本號、`N failed, M passed` 原文、worktree 路徑）。**不可只寫「測試通過」** |
| 4 | **是否觸及 `forces.py`（第五條）＋煙霧結果** | 觸及時必附 `TestHarnessSmoke` 結果、探針同步清單、ECC 側生成器比對結論；**不觸及時必須明寫「未觸及」**——這一欄的空白無法與「忘了檢查」區分 |

**格式（照本檔風格，可機械轉移）：**

```
【spectrum-os 待推交接】
commit: <40 碼>（短碼）
狀態: 本地已 commit／未推 origin master
第四條: worktree /tmp/fresh @<短碼> → pytest: <原文結果行>
第五條: 未觸及 kernel/forces.py
層級宣告（第七條）: <tooling/governance 等>
待人類: 授權 push origin master
```

#### 2.5.3 凍結期推送檢查（第八條的可執行接點——非機械強制）

**在解凍裁定之前，任何欲推 origin master 的提交，其交接清單必須附「凍結範圍裁定出處」。**

| 要附什麼 | 為什麼 |
|:---|:---|
| 本次提交不違反 09-11 凍結令的**逐項對照**（對照 8.1 的四要件：例外白名單／禁止清單／凍結理由／解凍前置） | 凍結令的禁止清單是**可枚舉的動作**（「不改 PARAMS、不加器械、不接時滯」）——逐項對照才叫證明，感覺不算證明 |
| 若屬例外白名單項：**該項的授權出處** | 白名單不回溯已授權項，但**「已授權」三個字需要出處** |
| 若凍結令無法回答「這算不算違反」（8.1 的規格不足訊號）：**先補列凍結令，再推** | 規格不足的凍結令不能拿來當擋箭牌，只能拿來當待辦 |

**為什麼這一節必須存在（此為審計發現，非事後發明）**：律文 v1.0 的第八條寫了凍結與解凍，第二條寫了推送順序，**但兩條之間沒有任何接點**——一個人在凍結期 commit，可以完全合法地走完第二條四步，把凍結期產物推上 origin master，而**本檔從頭到尾沒有一句話會亮紅燈**。凍結在 v1.0 是**文檔宣示**，不是**防線**；本節把它接成防線。**但這仍不是機械強制**——本節靠交接清單的人工執行，**沒有 pre-push hook 會攔你**；這是本檔「有紀律、無防線」的已知狀態之一（另兩處見 7.4.3 與 9.3）。

## 第三條 指針格式

ECC 側的 submodule pointer bump **必須是獨立、可辨識、名實相符的 commit**。

### 3.1 commit 訊息格式

```
[SPECTRUM-OS] pointer: <old7>→<new7>
```

- `old7`／`new7`：pointer bump 前後的 submodule commit hash **前七碼**。
- 訊息中**不得**夾帶其他改動的描述。pointer commit 只做 pointer。
- 若同一次確實還改了其他東西，**分成兩個 commit**——指針與內容不可混裝。

### 3.2 `.gitmodules` 設定

```ini
[submodule "spectrum-os"]
    ...
    ignore = untracked
```

原因：唯讀 checkout 產生的 `__pycache__` 等**未追蹤**檔案，會讓 ECC 出現假 `M spectrum-os` 訊號。`ignore = untracked` 消除假訊號，**真髒污（已追蹤檔案被改）仍會回報**——這正是我們要的：雜訊消失，警報保留。

### 3.3 為何要求「名實相符」

commit 訊息是**唯一的非同步通道**。人類與 agent 靠它判斷「這次動了什麼範圍」，然後決定要不要跟進、要不要重跑下游。訊息若低估範圍，**讀者按訊息規劃、實際 diff 卻大得多**——下一個問題就會在錯誤的前提上被回答。

### 🪦 事故墓碑：`2bdac138` 名不符實 pointer

- **症狀**：pointer commit 的**標題寫「pointer 收斂」**，實際 diff **包含 777 個檔案**。
- **傷害**：任何以訊息為準的審閱、二分定位、影響評估，全部失效。標題說「只動了指標」，實際是巨型改動被藏在最小標題下。
- **催生**：本條指針格式紀律。
- **教訓**：**標題就是承諾**。標題的範圍必須等於 diff 的範圍；做不到，就拆 commit。

## 第四條 提交完整性驗證

**規則：宣稱某個 commit 可用之前，必須在乾淨 worktree 上驗證它。**

```bash
git -C /home/octy/projects/spectrum-os worktree add /tmp/fresh <commit>
cd /tmp/fresh && pytest
git -C /home/octy/projects/spectrum-os worktree remove /tmp/fresh
```

### 🔴 「本機測試通過」≠「提交可通過」

工作樹同時含新舊檔案時，測試只證明**工作樹自洽**，不證明**提交自洽**。這是 `python -m pytest` 的結構性盲區——它在「有未提交改動的工作樹」上跑，看不到提交層的不一致。**只有乾淨 worktree 能重現「別人 clone 之後會看到什麼」。**

**觸發時機**：任何 commit 之後、宣告完成之前、push 之前。若第四條與第五條同時適用（改動觸及 `kernel/forces.py`），兩者都要跑。

### 6.2 「engine never fits parameters」（`kernel/forces.py:64`，條文引用）

> *Parameters (α, β, a, c, κ, μ, λ, ρ) are **SEMANTIC ANCHORS**, not physical constants: sign and relative magnitude carry the judgement; absolute values are neither available nor needed. **The engine never fits parameters.***

**推論（動態 lock 否決事件的裁定）**：既然參數是語義錨而非物理常數，那麼**用數據去反推／鎖定參數值，是把世界塞回引擎**。當有人提議「加一條動態 lock 把參數釘到實測值」時，該提議違反本條——**引擎不得 fit 參數**，參數的判準是符號與相對量級，不是擬合誤差。

- **症狀**：kernel 內直接出現 `co_share`／`debt_stress`／`sigma_soviet` 三個世界概念——違反 substrate 契約（世界只提供**形式**，引擎提供**結構**）。
- **催生**：kernel 零世界詞掃描＋substrate 化（`co_share` → `phi_drive`、`debt_stress` → `phi_suppress`，經 substrate callable 注入）。
- **教訓**：世界詞進 kernel 是**層級錯位**（見第七條），不是命名品味問題。

### 🪦 事故墓碑 B：ECC 絕對路徑內嵌 kernel

- **症狀**：兩支 kernel 模組帶 ECC 絕對路徑 → `test_sources` **持續失飛**。
- **催生**：`test_no_ecc_paths_in_core_modules`。
- **教訓**：核心模組不知道自己在哪台機器上——**一旦知道，它就不再是 OS**。

## 第七條 substrate 五層聲明制（v1.1 由四層擴為五層）

**每一項修改都必須聲明它屬於哪一層。五層：**

| 層 | 位置 | 內容 | 世界相關？ |
|:---|:---|:---|:---:|
| **kernel** | `spectrum_os/kernel/`、`spectrum_os/quantum/` | 世界無關的機制：頻譜→殘差→意外、ODE、Markov、量子層 | 🚫 **世界無關**（見 `PLAN.md:6`） |
| **substrate** | 世界側，如 ECC `scripts/ecc_substrate.py` | 世界的**形式**，以 callable 注入：`c_source_fn`／`k_inflow_fn`／`phi_drive_fn` 等 substrate 槽 | ✅ 世界特定 |
| **extensions** | `spectrum_os/extensions/` | 外掛動力學：`gnp_dynamics.py`、`ar_frigorifico_dynamics.py`、`market_suite_dynamics.py` | ✅ 世界特定（**可選、可插拔**） |
| **🆕 tooling/governance** | 見 7.4 的四類落點 | 生成器／驗證器／掃描器／沙盒線束／同步檢查器——**不產生頻譜值的工具** | 🚫 引擎與世界皆非（見 7.4 判準） |
| **data** | 卷宗／觀測／校準輸入、工具產出的報表 | 具體數值、時間序列、快照 | ✅ 世界特定 |

### 7.1 聲明義務

**每次修改必須在 commit 訊息或 TASKLOG 條目中明確聲明層級。** 範例：

```
[Forces] kernel 層：FastChannelConfig 新增 phi_drive 槽（世界無關，substrate 注入）
[Forces] substrate 層：ecc_substrate.py 以 phi_drive_fn 取代 co_share 常數
[Tooling] tooling/governance 層：validate-almanac-volumes.py 新增 set 感知檢查
```

**未聲明層級 = 未完成修改。**

### 7.2 🔴 錯層即事故

**同一件事放錯層，就是事故**——不是風格問題，是**架構破壞**：

| 錯層 | 後果 |
|:---|:---|
| 世界概念寫進 kernel | kernel 不再世界無關 → OS 退化為「ECC 的內部工具」→ 第六條紅燈 |
| 引擎機制寫進 substrate | 世界側重複實作引擎邏輯 → 每個世界各自實作一遍 → 無法比較 |
| 世界概念寫進 extensions 又反向依賴 kernel | 外掛不再是外掛 → 可插拔性消失 |
| 🆕 **工具邏輯寫進 kernel** | 生成器／驗證器的便利函數住進核心 → **核心開始為某一支工具而長** → 第六條紅燈（且比第一列更隱蔽：工具邏輯看起來「世界無關」） |
| 🆕 **工具冒充 data** | 工具**是世界的代碼卻假裝不是**——它跑世界的資料、輸世界的結論，卻用「只是工具」的名義規避 7.1 聲明 → **比錯層更壞：這是逃避聲明制本身**（見 7.4.3 第 3 條） |

### 7.3 📌 註記：本條同時是 substrate 契約規格化的起點

**現行 substrate 契約僅一句聲明**（`docs/PLAN.md:6`）：

**這句話確立了原則，但沒有定義介面。** 目前 substrate 契約的**實際**內容散落在：`kernel/forces.py` 的 substrate 槽 docstring（`growth_c_fn`／`release_fn`／`phi_drive` 等）、`ECC/scripts/ecc_substrate.py` 的實作、以及 `tests/test_forces_fast_channel.py` 的介面測試。

### 7.4 🆕 tooling/governance 層（v1.1 新增）

#### 7.4.1 為什麼要新增這一層：四層制的分類真空

**律文 v1.0 的四層（kernel／substrate／extensions／data）不是 MECE 的——它漏掉了「工具」。** 以下三類東西**四層都裝不進去**：

| 類 | 實例 | 歸不進去的理由 |
|:---|:---|:---|
| **生成器** | `pilot-1920-gen.py`、`build_residual_table.py`、`stage3_*_pilot.py` | 不是 kernel（它們有世界詞、知道 1920、知道薩拉熱窩）；不是 substrate（substrate 是**世界的 callable 形式**——被引擎**注入**的函數；生成器**不被注入**，它在外面跑，把 recipe 組織起來去**呼叫**引擎）；不是 extensions（外掛動力學是引擎在回合中**載入並執行**的動力學，生成器不參與單回合動力學） |
| **治理驗證工具** | `validate-almanac-volumes.py`、`check-spectrum-os-sync.sh` | 不是 kernel（世界無關）。**註**：前者的真本體不在本 repo（實測落於 ECC `scripts/`，見附錄 B 第 12 列），本層收的是它的**類**——治理工具住在消費者側是常態，因為**消費者才持有被治理的佈局**（同第一條的違反偵測邏輯） |
| **實驗線束／沙盒** | `sandbox-dynamics.py`、`falsify009_rupture_experiment.py`、`sarajevo_branch_experiment.py` | 不是進生產的動力學（不屬 extensions）；卻也不只是 data（它**跑**引擎、**組織**實驗），單歸 data 會丟掉它的可執行性 |

**四層制把這些東西逼進兩條路：謊報層級，或不聲明。** 兩條路都讓 7.1 的聲明義務（「未聲明層級＝未完成修改」）失效——**當層級表裝不下真實的東西，聲明就變成填表遊戲。**

#### 7.4.2 五問決策樹（層級判定程序）

**逐問往下；任一問答「是」即定層，第一問即終止。**

| 問 | 若「是」→ | 判準的核心 |
|:---:|:---|:---|
| **Q1** 是世界無關的動力學核心？（任何世界都跑同一套機制；換世界不改一行） | **kernel** | 世界詞出現即不成立（第六條紅燈） |
| **Q2** 是世界的 **callable 形式**？（被引擎**注入**的函數槽：`c_source_fn`／`k_inflow_fn`／`phi_drive_fn`） | **substrate** | **「被注入」是關鍵動詞**——寫一個 function 給引擎呼叫 |
| **Q3** 是外掛通道？（引擎在回合中載入並執行的可選動力學） | **extensions** | 可插拔：拔掉它引擎仍跑 |
| **Q4** 是工具或治理？（生成器／驗證器／掃描器／沙盒線束／同步檢查器——**跑引擎、驗引擎、掃引擎，但不是引擎本身**） | **tooling/governance** | **既不進 kernel 契約，也不提供可注入形式**——它在外面**操作**引擎 |
| **Q5** 以上皆非 | **data** | 剩下的就是具體數值、時間序列、快照 |

**決策樹的意義**：把「聲明層級」從**記憶題**變成**程序題**。v1.0 的四層表要求聲明者自己判斷，而判斷的邊界（尤其 substrate vs extensions）本就是本檔中**最需要人工解釋**的地方——**留白的地方，人就各自填空**。

**Q2 與 Q4 的邊界（最容易混的一條）**：substrate 交出的是**引擎會呼叫的函數**；tooling 交出的是**呼叫引擎的程式**。方向相反：**substrate 向內（被引擎 call），tooling 向外（去 call 引擎）。** `ecc_substrate.py` 是前者，`pilot-1920-gen.py` 是後者。

#### 7.4.3 本層紀律（三條）

**本層的自由度刻意高於 kernel——但自由不是免責。**

| # | 紀律 | 內容 |
|:---:|:---|:---|
| 1 | **可自由演化** | 工具層**不受 kernel 契約約束**：可重寫、可棄用、可隨世界變化。kernel 改動要走第六條＋第四條＋第五條；工具改動**只需**聲明層級（7.1）＋產物重生成（第 2 條） |
| 2 | **不進 kernel 契約** | 工具層**不得**成為 kernel 的依賴——`tests/test_sources.py::test_no_ecc_paths_in_core_modules` 的守備範圍**不得**擴及工具層本身，否則等於用測試把工具凍進核心 |
| 3 | **🔴 影響記錄義務** | 這是本層**唯一**的硬性義務：**變更工具時，必須記錄它影響哪些產物，並執行產物重生成** |

**為什麼第 3 條是硬性的**：工具層的危險**不在它自己壞，而在它產出的東西沒人重新檢查**。工具改一行、輸出靜默變值，而 data 層的檔案仍掛著舊日期——**下游讀到的是「工具的舊版語義 ＋ 檔案的新版時間戳」**，這個組合在任何單一檔案裡都看不出矛盾。

**與第四條的區別（別搞混）**：第四條問「**提交**能不能通過」，7.4.3 問「**產物**要不要重跑」。兩者不互相取代——工具層改動兩者皆適用。

**重生成義務的機械接點（現有，不新增腳本）**：本 repo 現有的 **同步檢查器**（`check-spectrum-os-sync.sh`）已經在盯工作樹的漂移；**工具層改動的重生成義務與它是同一條神經**——漂移被檢出時，該問的不只是「pointer 為何 stale」，還有「**工具改過之後，產物重生成過了嗎**」。

> **本層的裂縫（誠實記錄，不修辭）**：**7.4.3 第 3 條目前沒有機械強制器**——沒有腳本會因為「產物沒重生成」而亮紅燈。這與第二條 2.5.3 同類：**都是「有紀律、無防線」的狀態**。列在此處，是為了讓下一個發現它的人知道**這是已知缺口，不是他漏看了一條**。

## 第八條 凍結與解凍程序（本檔首立）

### 8.1 凍結令：必須明列範圍

**凍結令不得寫成「引擎凍結」四個字。** 必須回答：**不改什麼、不改到什麼程度、為何凍結、解凍前置是什麼。**

**照 09-11 體例**（`SESSION-START-20260911.md:231`）：

> **引擎凍結範圍**：除已完成的 P2 池地板外，**不改 PARAMS、不加器械、不接時滯**——等數據，不磨刀。

拆解此體例的四個要件：

| 要件 | 該例的內容 |
|:---|:---|
| ① **例外白名單** | 「除已完成的 P2 池地板外」——凍結令不回溯已授權項 |
| ② **禁止清單（具體動詞）** | 「不改 PARAMS、不加器械、不接時滯」——**不是「不優化」，是可枚舉的動作** |
| ③ **凍結理由** | 「等數據」——凍結是**等待約束解除**，不是「不要動」 |
| ④ **隱含解凍前置** | 數據到位（P3 的 1920 實測 observation 卷） |

**違反偵測**：若凍結令無法回答「這算不算違反？」——例如有人提議「只是重構一下 `forces.py`，不算改參數吧」，而凍結令沒說——則該凍結令**規格不足**，應補列。

### 8.2 解凍程序（無先例，本次首立）

**09-11 凍結令下達至今，尚無解凍先例。以下為首立程序：**

1. **須用戶明示裁定**——解凍**不可由 agent 自行判斷**「數據好像夠了」。凍結的解除是**裁定**，不是推論。
2. **裁定必須限定範圍**：**定點解凍**（指定具體條目，如「解凍時滯耦合」）或**全面解凍**（明文寫「全面」）。**未限定的解凍令視為規格不足**，應回問——因為「解凍」的預設語義歧義：是指凍結令全部項目解除，還是僅指某項解除？
3. **解凍後，先跑兩項驗證**（理由見下）：
   - **第五條煙霧**：`pytest tests/test_forces_fast_channel.py::TestHarnessSmoke` ＋同步探針 ＋ ECC 側生成器比對；
   - **第四條 worktree 驗證**：`git worktree add /tmp/fresh <commit> && pytest`。

**為何解凍後必跑這兩項**：凍結期間引擎**未被觸碰**，但也**未被驗證**。基礎設施（探針、ECC 側生成器、Python 版本、依賴）在凍結期間持續變動——凍結只凍結了引擎，沒凍結環境。**解凍後的第一次改動，同時是環境漂移的第一次曝光**。這兩項驗證是曝光的手段。

### 8.3 凍結與解凍的關係

```
凍結令（範圍明列） ──→ 凍結期（引擎不動，環境在動） ──→ 用戶裁定解凍（定點/全面）
                                                              ↓
                                                第五條煙霧 + 第四條 worktree
```

**凍結不是「暫停」，是「把引擎釘在一個已驗證的座標上」**——因此解凍時必須重新證明那個座標還在。

### 9.4 版本號與 diff 留痕

| 規則 | 內容 |
|:---|:---|
| **版本號** | **次版號 +0.1**：條文語義變更、新增條文、增刪層級（如 v1.0→v1.1 為「四層→五層＋新增條」）。**+0.0.1**：座標修正、錯字、引用更新（§9.1 丁類）。**主版號 +1.0** 見 9.4.1，**門檻未達前不得使用** |
| **檔頭版本行** | 版本行必須記日期，格式 `v<次版>（YYYY-MM-DD）`。**此行的日期與 commit 日期不同時，以 commit 日期為準** |
| **修訂記錄** | 檔尾「修訂記錄」節（固定位置，永遠在最後）：每版一列，含版本／日期／commit／動機（§9.1 類型）／修訂項清單 |
| **🔴 自指條款（(HEAD) 佔位機制，v1.2 新增）** | **當前版本的修訂記錄，其 commit 欄標準化填寫 `(HEAD)`**——hash 由**下一次修訂**回填（即「上一版的 hash 在下一版的記錄中出現」，**鏈式回填，永不自指**）；release/tag 時依 **9.4.2 release 邊界豁免**處理（v1.3 修訂——原「由人類核對最後一列的 `(HEAD)` 已被回填」的要求在字面上是死循環，回填即新 commit、新 commit 即新 `(HEAD)`）。**嚴禁以 `git commit --amend` 回填 hash**——amend 改變 hash ＝ 剛寫下的記錄立刻失效 ＝ 製造舊 hash 的孤兒殘影，違反第二條反歷史改寫的精神。v1.1 的兩次 amend 即此條的誕生代價（見檔尾「v1.1 的 commit hash 悖論」） |
| **commit 訊息** | 格式如下（與第三條同族的「標題即承諾」原則——**標題的範圍必須等於 diff 的範圍**）： |

```
[Docs] 修改律 v<舊>→v<新>：<一句話說明修訂項數與主題>
```

**9.4.1 主版號門檻（未達，不得使用）**：主版號 +1.0 **保留給「紀律架構的整體重寫」**——即**超過半數條文被改寫、或層級體系被重新定義**的修訂。**「條文數量多」不是門檻**：v1.1 動了三條（第二／七條修訂＋第九條新增），**仍是 +0.1**。

### 9.4.2 release 邊界豁免（v1.3 新增，動機：乙類審計發現——agy 終審）

**自指條款在 release/tag 情境下是死循環**：核對「最後一列 `(HEAD)` 已被回填」→ 回填本身就是一次修訂 → 新 commit → 修訂記錄又出現新的 `(HEAD)` → 核對永遠失敗。**一個在 release 時永遠不通過的檢查，不是防線，是逼人說謊的機器。**

**豁免規則**：

| 情境 | 規則 |
|:---|:---|
| **release/tag** | 允許修訂記錄**最後一列保留 `(HEAD)` 字樣**——tag 本身就是版本錨點，`git rev-parse <tag>` 即該版的事實 hash（SSOT 仍是 git 歷史，本檔不造第二真相源），**不需要 hash 回填** |
| **release 的條件** | 該 release 的 commit 訊息必須附 **`closes: HEAD`** 標記——聲明「本 commit 的修訂記錄以 `(HEAD)` 收尾、由 tag 錨定」，使未回填成為**可機械辨識的明示狀態**，而非遺漏 |
| **正常（非 release）修訂** | 照自指條款鏈式回填，不受本豁免影響 |

**為什麼不是「改用 tag 名回填」**：tag 是 repo 狀態不是檔案內容——把 tag 名寫進修訂記錄等於在文檔裡維護第二份指針，漂移風險同第三條 3.3 的名實不符。**`(HEAD)`＋`closes: HEAD` 讓「未回填」從意外變成聲明**，這才是本豁免的全部。

### 9.5 修訂記錄的位置（單一 SSOT）

```

```

**修訂記錄要求每版記 commit hash；但 hash 在 commit 之後才存在——記錄本身是這次 commit 的一部分。** 這是**自指的不動點問題**，v1.1 是第一次撞上它：

| 嘗試 | 結果 |
|:---|:---|
| ① 先 commit，再回填 hash 並 amend | **amend 會改變 hash**（`4a5c269` → `d35ee14`），回填的 hash 立刻失效——**改一次改不掉，改兩次會再變** |
| ② 記錄寫「見 git log」 | 免除自指，但**違反 9.4「修訂記錄須含 commit」的字面要求**，且讀者必須自己撈 |

**現行裁決（v1.1 採用 ② 的變體，並在此說明；⚠️ v1.2 起此變體由 §9.4 自指條款的 `(HEAD)` 機制取代，見節末 ✅ 裁決）**：**本檔的修訂記錄對「本次 commit 自身」採引用式記載**——hash 的事實來源是 `git log`，理由是：

1. **本檔的第一條已經原則在案**：「真本體＝唯一可寫入的 checkout」，git 歷史是 hash 的 SSOT——**在文檔裡再寫一份 hash，等於製造第二個真相來源**；
2. **回填 hash 必然引入 amend**，而 amend 在未 push 的本地 commit 上會**改寫歷史、製造舊 hash 的孤兒殘影**——這正是第二條的孤兒風險，只是規模小；
3. **v1.0 的 hash（`1f4144d`）之所以能寫死，是因為它是「過去的 commit」**；**「當下的 commit」寫不進自己**。

**9.4 的已知空洞**：9.4 要求「修訂記錄含 commit」卻**未區分「過去的版本」與「本次版本」**，也未規定 amend 是否合法。**本輪不擅自補這個洞**（那會讓 v1.1 為了修律而擴權），**只登錄它**——依 9.3 第 4 步，這是合法的「記錄裂縫，不改條文」。**下一次修訂應為 9.4 補「自指條款」。**

**✅ v1.2 裁決（上述空洞已補，本節由「裂縫」轉為「墓碑」）**：v1.2 已依 §9.4 新增的**自指條款（(HEAD) 佔位機制）**修復——修訂記錄的 commit 欄自此**區分「過去的版本」（寫實際 hash，由下一次修訂回填）與「本次版本」（標準化填 `(HEAD)`）**；**amend 回填明文禁止**。v1.1 列的 commit 欄已回填 `f8886f3`——**這是鏈式回填機制的第一次實際執行**（v1.1 的 hash 由 v1.2 的記錄攜帶，永不自指）。v1.1 的「引用式記載」變體（② 的變體）自本版起**由 `(HEAD)` 機制取代**；release/tag 時由人類核對最後一列的 `(HEAD)` 是否已被回填。
